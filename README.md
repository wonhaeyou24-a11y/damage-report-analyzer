# 보고서 손상분석 프로그램

손상 그룹(보고서 원문 번호)을 개별 위치별 손상 레코드로 분리하고, 부위/세부부위/위치를 구조화하여
Excel처럼 검토할 수 있는 웹 앱입니다.

## 실행

```bash
npm install
npm run dev
```

브라우저에서 `http://localhost:5173` 접속 후 "샘플 데이터로 미리보기"로 동작을 바로 확인할 수 있습니다.
실제 보고서를 분석하려면 Claude API 키와 PDF 파일을 업로드하고 "분석 시작"을 누릅니다. API 키는
브라우저 로컬 저장소에만 저장되며 서버로 전송되지 않습니다.

## 데이터 파이프라인

```
PDF 업로드 (src/lib/pdf.ts, pdfjs-dist)
  → 페이지별 텍스트 추출
  → Claude API 프롬프트 (src/lib/aiPrompt.ts) — 손상 그룹 단위로 추출, 부위 표준값 강제,
    위치 콤마 분리 지시, 범위는 유지, 물량은 그룹/개별 구분, 사진은 1차 그룹 관계만
  → RawDamageGroup[] (src/lib/claude.ts)
  → expandAllGroups() (src/lib/normalize.ts) — 그룹을 개별 DamageRecord[]로 분해
  → DamageTable (src/components/DamageTable.tsx, AG Grid) — 검토/수정/필터/내보내기
```

## 핵심 데이터 모델 (src/types.ts)

- `DamageRecord`: `part`(표준 부위) / `subPart`(원문 시설명) / `location`(개별 위치)을 분리해서 보관.
- `quantity` vs `quantityGroup`: 개별 위치에 물량이 명시된 경우만 `quantity`, 그렇지 않으면
  그룹 총 물량을 `quantityGroup`(예: "그룹 합계 23.3m에 포함")에 담아 반복 입력을 방지.
- `groupNo` + 개별 접미사(`③-01`)로 원문 그룹 구조와 개별 손상을 동시에 추적.
- `sourcePages` / `sourceReferences`로 원문 출처를 유지 (테이블의 🔎 버튼으로 확인).
- `photos[].linked`로 그룹 단위 연결과 개별 손상 연결을 구분.

## 위치 분리 규칙 (src/lib/normalize.ts)

- 콤마로 나열된 위치는 각각 분리 (`165, 187, 188m` → 3건).
- `176~206m` 같은 범위는 하나의 위치로 유지 (쪼개지 않음).
- 세부부위가 줄바꿈으로 바뀌는 블록(`도수로 208m`, `산마루측구 211, 323m`)도 분리 파싱.
- 부위는 표준 분류값(`상부자연사면/사면/사면하부/보강시설/보수시설/배수시설/기타`)만 허용하며,
  매칭 실패 시 "기타"로 지정하고 `notes`에 원문 값을 남겨 검토 상태로 표시.

## 테스트

`npm run test` (vitest) — 개발 스펙 16번 항목의 검증 시나리오를 커버:

1. 위치 8개 → 개별 레코드 8건
2. 동일 손상명 + 다른 세부부위 → 별도 레코드
3. 동일 손상명 + 다른 부위 → 별도 레코드
4. 범위 위치(`176~206m`)는 하나로 유지
5. 그룹 총 물량은 각 행에 중복 입력되지 않음
6. 단일 위치 그룹은 접미사 없이 그룹 번호 그대로 사용
7. 표준값에 없는 부위는 "기타" + 검토 필요로 표시

## 화면 기능 (src/components/DamageTable.tsx)

컬럼: No / 구간 / 손상명 / 부위 / 세부부위 / 위치 / 보수방안 / 규모·물량 / 사진 / 출처 / 상태 / 삭제

- 정렬 · 필터 · 검색(quick filter) · 셀 인라인 수정 · 행 추가 · 행 삭제
- 개별 손상 보기 / 그룹별 보기(그룹당 대표 1행) 전환
- 검토필요만 보기 필터
- 사진 미리보기 모달(개별 손상에 사진 직접 업로드 가능, 그룹/개별 연결 구분)
- 출처 모달(페이지 번호 · 유형 · 원문 발췌)
- CSV 내보내기(AG Grid 내장) / Excel 내보내기(SheetJS)

## STEP 5 — 중복 통합 / 다중 페이지 통합 / 불일치 검출 (src/lib/mergeDuplicates.ts)

- 구간+손상명+부위+세부부위+위치가 완전히 같은 레코드만 하나로 통합하고, 보수방안/수량/출처를
  결측값 우선 채우기 방식으로 결합한다 (STEP4 출력 뒤에 자동 연결).
- 위치만 다르지만 서로 겹치지 않는 출처 페이지에서 나온 경우에만 "같은 손상을 다르게 보고했을 가능성"으로
  보고 `location: "검토필요"` + `conflicts`로 표시한다. 같은 페이지 목록에서 나열된 서로 다른 위치는
  절대 합치지 않는다.
- 결과 화면(`DamageTable`)에 통합/불일치 컬럼과 6종 검토 필터(전체/확정/검토필요/정보불일치/중복통합/
  출처확인필요)가 추가되었다.

## STEP 6 — 손상사진 추출 및 사진 메타데이터 (src/lib/photoExtraction.ts, photoAnalysis.ts)

- PDF의 각 페이지에서 operator list를 분석해 임베디드 이미지의 위치(bounding box)를 찾고, 페이지
  렌더링 결과에서 해당 영역만 크롭해 사진 단위로 분리한다 (한 페이지에 여러 사진이 있어도 개별 추출).
- 사진 주변 텍스트에서 사진번호(③-01, 사진 1, No.1, P-01 등)/캡션/위치/손상명/세부부위를 정규식으로
  파싱한다. 문서에서 확인되지 않은 값은 만들어내지 않고 `null`로 남긴다.
- 주변 텍스트가 없는 사진만 선택적으로 OCR(tesseract.js)을 수행해 비용을 절약한다.
- 이미지 average hash로 중복 후보를 탐지한다 (사진번호가 아니라 실제 이미지 유사도 기준).
- STEP7에서 쓸 손상-사진 매칭 점수(`matchCandidates`)를 미리 계산해두지만 `linkedDamageIds`는
  STEP6에서 항상 비워둔다 (확정 연결은 STEP7의 역할).
- Vision 분석(Claude 멀티모달)은 자동 실행하지 않고, 사진 상세 모달에서 사용자가 선택적으로 실행한다
  (비용/성능 방침). 결과는 `visionInference`로 분리 저장하여 보고서 원문 사실과 구분한다.
- "사진 목록" 탭(`PhotoGallery`)에서 사진번호/페이지/캡션/위치/손상관련성/중복후보/상태를 확인하고,
  클릭하면 원본 이미지·OCR·주변 문맥·출처·Vision 분석을 볼 수 있다.

## STEP 7 — 손상↔사진 자동 연결 및 검증 (src/lib/matchPhotos.ts)

- STEP6의 `computeMatchScore`를 스펙 8번 가중치(사진번호+30/손상명+20/세부부위+15/위치+20/구간+5/
  캡션+10/OCR+10/문맥+5)로 재조정하고, "확실한 핵심 근거만으로 완전 일치"했을 때 100%가 되도록
  정규화 기준(`MAX_MATCH_SCORE`)을 잡아 신뢰도(confidence)를 계산한다.
- 신뢰도 ≥0.90 이고 하드 충돌이 없으면 `confirmed`(자동 연결), ≥0.70이거나 충돌이 있으면 `review`,
  그 외 `unmatched`로 분류한다 (`DEFAULT_THRESHOLDS`에서 값 조정 가능).
- **하드 충돌(`hasHardConflict`)**: 사진번호 또는 세부부위로 "같은 대상으로 보이는" 앵커가 이미 있는
  경우에만 위치/세부부위 불일치를 충돌로 판단한다. 애초에 무관해 보이는 사진-손상 쌍은 위치가 달라도
  충돌로 보지 않고 그냥 `unmatched`로 둔다 — 점수가 높아도 이 충돌이 있으면 자동 확정하지 않는다.
- 위치 표기(165m/STA.165m/K165/165.0m 등)를 정규화해서 비교하고, 범위(`176~206m`) 포함 여부는
  약한 참고 신호로만 사용해 자동 확정 근거로 쓰지 않는다.
- 사진 1장이 여러 손상과, 손상 1건이 여러 사진과 연결되는 것을 모두 허용한다(임계값을 넘는 모든
  후보를 연결하며 상위 1건으로 강제로 좁히지 않음).
- `damage.photoIds`/`photoMatchStatus`는 `photos[].linkedDamageIds`로부터 매번 파생시켜(`deriveDamagePhotoLinks`)
  단일 진실 공급원을 유지한다 — 수동 연결도 자동으로 손상 쪽에 반영된다.
- **수동 연결이 항상 우선**: `manuallyLinkPhoto`/`manuallyUnlinkPhoto`로 사진을 수정하면 `manualOverride:true`가
  설정되고, 이후 `matchPhotosToDamages()`를 다시 돌려도 해당 사진은 자동 재분석 대상에서 제외되어
  사용자 결정이 절대 덮어써지지 않는다. `setDamageNoPhoto()`로 손상을 "사진 없음"으로 직접 지정할 수도 있다.
- **UI**: 손상 목록의 "사진" 컬럼이 연결 상태 아이콘(🟢확정/🟡검토/🔴충돌/⚪없음)을 보여주고, 클릭하면
  연결된 사진·후보 사진(점수/근거 포함)·"사진 없음" 지정을 한 곳에서 처리하는 모달이 뜬다. 사진 목록
  화면에서도 같은 연결/해제를 할 수 있다. 상단에는 전체 매칭 통계(손상: 연결완료/검토/없음, 사진:
  손상사진/연결완료/미연결)를 표시한다. 검토 필터에 "사진 연결 검토"/"사진 없음"이 추가되었다.

## STEP 8 — 추가자료 교차검증 (선택사항) (src/lib/crossValidate.ts, src/lib/additionalDocs/)

- **완전히 선택사항**: `AdditionalDataPanel`의 체크박스를 켜지 않으면 아무 것도 실행되지 않고, 켜지
  않았거나 자료를 첨부하지 않은 손상은 `crossValidation`이 `undefined`로 남아 "건너뜀"을 자연스럽게
  표현한다 — 오류로 취급하지 않는다.
- **첨부와 분석 분리**: 파일 첨부(`+ 추가자료 첨부`) → "첨부 파일 분석" → "교차검증 시작" 세 단계가
  분리되어 있어, 파일을 올렸다고 자동으로 검증이 시작되지 않는다.
- **지원 형식**: PDF(`pdfjs-dist` 텍스트 레이어 재사용), Excel(`xlsx`, 시트/헤더/셀 구조 유지),
  Word `.docx`(`mammoth` + `DOMParser`로 표 구조 유지). `.doc`(97-2003 바이너리)는 브라우저에서 직접
  파싱할 수 없어 "분석 실패"로 표시하고 나머지 파일은 계속 분석한다.
- **자료 종류 자동 분류**: 파일명 + 내용 키워드로 외관조사망도/사진대지/보수보강표/수량표/도면/
  종합결론/기타를 추정하고, 확신이 낮으면 신뢰도 값과 함께 "기타"로 남긴다(파일 자체는 계속 분석).
- **표 구조 인식**: Excel 시트/Word 표 모두 헤더 행(구간/부위/세부부위/손상명/위치/보수공법/수량 등)을
  키워드로 인식해 행 단위 손상 후보를 만든다. 헤더를 인식하지 못해도 각 행을 텍스트로 스캔해 최소한의
  후보라도 만든다.
- **매칭/충돌 판정**: STEP7과 같은 원칙 — 세부부위 또는 사진번호처럼 "동일 대상"을 특정하는 강한
  앵커가 있을 때만 위치/손상명 차이를 충돌로 본다. 무관해 보이는 후보의 필드가 다른 것은 충돌이
  아니라 그냥 무관한 것으로 처리한다. 충돌은 점수와 무관하게 자동 확정을 막는다.
- **결과 유형**: `matched`/`conflict`/`missingInAdditional`/`candidate`/`unsupported` — "추가자료에
  없음"을 "손상 없음"으로 해석하지 않는다.
- **누락 후보**: 어떤 기존 손상과도 세부부위/위치/사진번호가 겹치지 않는 추가자료 후보는 `CandidateDamage`로
  모아 사용자 승인 전까지 손상 목록에 추가하지 않는다(`approveCandidateDamage`).
- **수동 해결이 항상 우선**: `resolveCrossValidationConflict()`로 사용자가 "기본값 유지"/"추가자료 값
  채택"을 고르면 해당 필드가 실제로 갱신되고 `resolved` 마크가 남아, 교차검증을 다시 실행해도 그
  불일치가 다시 검토 대상으로 올라오지 않는다.
- **UI**: 손상 목록에 "교차검증" 컬럼(🟢일치/🔴불일치/🟡미확인/⚪검증불가) 추가, 클릭 시 근거 자료
  목록·불일치 표(기본 보고서 vs 추가자료 값)·해결 버튼을 보여주는 모달. 검토 필터에 "교차검증 불일치"/
  "추가자료 미확인" 추가. 상단 통계에 교차검증 대상/일치/불일치/미확인 건수 표시.

## STEP 9 — 최종 검토/검수 (src/lib/finalReview.ts, src/components/FinalReviewBar.tsx)

- **새 데이터 구조를 만들지 않음**: STEP1~8의 `damageRecords`/`photoRecords`/`additionalDocuments`/
  `candidateDamages`를 그대로 재사용한다. `DamageRecord`에 `fieldOverrides?`/`reviewHistory?`만
  추가하고, 보고서 단위 메타데이터(`ReviewSession`)만 별도 최상위 상태로 둔다.
- **필드별 원본값 보존**: 셀을 수정하면 `recordFieldEdit()`가 "최초 AI 값(originalValue)"과 "현재 값
  (currentValue)"을 분리 기록한다. AG Grid는 `onCellValueChanged`가 호출되기 전에 행 객체를 이미
  새 값으로 바꿔버리므로, `e.oldValue`(수정 직전 값)를 명시적으로 넘겨 받아야 원본이 사라지지 않는다
  — 개발 중 실제로 이 문제가 발생해 발견 후 고쳤다(테스트로 회귀 방지).
- **위치 숫자 정렬**: `compareByLocation()`이 "65m/110m/165m/208m/211m"처럼 문자열이지만 숫자로
  정렬되게 하고, 범위(`176~206m`)는 시작값 기준, 파싱 불가(`검토필요`)는 맨 뒤로 보낸다.
- **검색**: `searchDamages()`가 손상명/구간/부위/세부부위/위치/보수방안뿐 아니라 연결된 사진의
  사진번호·페이지까지 검색 대상으로 삼는다(AG Grid 내장 quickFilter로는 안 되는 부분이라 새로 구현).
- **필터 확장**: 기존 STEP5/7/8 필터에 제외됨/위치 문제/사진 문제/규모 문제/직접입력 손상을 추가했다.
- **일괄 검수**: 선택한 행에 대해 "일괄 검수 완료"(`bulkConfirm`, 충돌 상태는 강제로 확정하지 않음)와
  "일괄 사진 없음 확인"(`bulkMarkNoPhoto`, 기존 STEP7 `setDamageNoPhoto` 재사용)을 제공한다.
- **후보 손상 결정**: STEP8의 "무시" 버튼을 "제외"/"검토 보류"로 분리했다 — 둘 다 후보를 배열에서
  삭제하지 않고 `decision` 필드만 남긴다. 승인 시 중복 검사(구간+손상명+부위+세부부위+위치)를 거쳐
  이미 존재하는 손상이면 새로 만들지 않고 출처만 병합한다(`approveCandidateDamage`에 추가).
- **충돌 화면에 "직접 수정" 추가**: 기존 "기본값 유지"/"추가자료 값 채택" 버튼 옆에 텍스트 입력+확정
  버튼을 추가했다. 세 경로 모두 `resolveCrossValidationConflict()`로 수렴하며 `resolved.decidedAt`을
  남긴다.
- **최종 확정 게이트**: `canFinalize()`가 (1) 미해결 충돌(STEP5 status="conflict" 또는 STEP8
  reviewRequired) (2) 미결정 후보 (3) 필수 필드 누락 (4) 사진 연결 충돌을 검사한다. 사진이 없는 손상
  자체나 미연결 사진은 막지 않는다(스펙 20번 원칙 그대로 구현, 테스트로 확인).
- **검수 완료 vs 최종 확정**: "검수 완료"는 `ReviewSession.finalReviewStatus`만 "completed"로 바꿔
  "최종 확정" 버튼을 활성화하고, "최종 확정"은 게이트 통과 시 `finalizeReview()`로 `finalizedAt`/
  `finalizedBy`/`reviewVersion`을 기록한다.
- **재분석의 범위**: [재분석]은 STEP7(`matchPhotosToDamages`)과 STEP8(`runCrossValidation`)을 현재
  데이터로 다시 계산할 뿐, STEP4의 AI 텍스트 추출 자체를 다시 실행하지 않는다(원본 PDF를 다시 읽지
  않고, 이미 계산된 결과만 최신 상태로 갱신). `manualOverride`/`resolved`는 항상 보존된다.
- **STEP10 연결용 선택자**: `getFinalizedDamageRecords()`/`getFinalizedPhotoRecords()`/
  `getFinalValidationResults()` — 기존 배열을 필터링만 해서 반환하며 새 구조를 만들지 않는다.
- **Inspector**: 손상 행의 "상세" 버튼이 기본정보/AI 분석정보/사진/교차검증/출처/검수 기록/사용자
  수정값을 한 모달에 모아 보여준다(기존 개별 모달은 빠른 접근용으로 그대로 유지).

## STEP 10 — 최종 데이터 출력 (Excel/Word/PDF) (src/lib/report/, src/components/FinalOutputPanel.tsx)

- **출력 대상은 항상 STEP9의 "최종 확정 데이터"**: `buildFinalDataset()`이 `getFinalizedDamageRecords`/
  `getFinalizedPhotoRecords`(STEP9)를 그대로 불러 쓰고, `scope:"selected"`일 때만 선택된 No로
  더 좁힌다. AI 최초 추출 결과를 직접 출력하지 않는다.
- **세 출력 형식이 데이터 모델을 공유**: `buildDataset.ts`의 `buildDamageRows`/`buildPhotoRows`/
  `buildCrossValidationRows`/`buildSourceRows`/`buildReviewHistoryRows`를 Excel(`exportExcel.ts`)·
  Word(`exportWord.ts`)·PDF(`exportPdf.ts`)가 모두 그대로 재사용한다 — "동일한 데이터 모델 사용,
  변환 로직 중복 금지" 원칙을 그대로 구현했다.
- **출력 전 무결성 검사**: `validateForExport()`가 STEP9 `canFinalize()`(미해결 충돌/미결정 후보/필수
  필드 누락/사진 연결 충돌)에 더해 출처 누락, 존재하지 않는 사진 참조(데이터 구조 오류)까지 검사한다.
  문제가 있으면 "최종 출력 전에 해결해야 할 항목이 있습니다"를 이유와 함께 보여주고 **파일을 만들지
  않는다** — 조용히 잘못된 파일을 생성하지 않는다.
- **그룹 물량**: `quantityGroup`에 이미 저장된 "그룹 합계 23.3m에 포함" 형태를 그대로 출력하고, 개별
  행에 23.3m를 반복하지 않는다(테스트로 확인).
- **사진 처리**: Excel 손상목록 시트는 사진번호/건수만 표시하고, 실제 이미지는 손상사진 시트(파일명·
  캡션·연결상태·confidence)와 Word 상세 섹션에만 넣는다. 한 사진이 여러 손상에 연결돼도 동일
  `photoNo`/원본 데이터를 참조할 뿐 파일을 중복 저장하지 않는다. 미연결 사진은 옵션(`includeUnlinkedPhotos`,
  기본값 포함)으로 별도 표시한다.
- **충돌/후보 출력**: 사용자가 해결한 충돌은 최종 값이 출력되고, 교차검증/검수이력 시트·섹션에는 주
  보고서 값·추가자료 값·사용자 결정이 모두 남는다. `candidate`는 승인된 것만 손상목록에 포함되고,
  제외/보류 결정은 검수이력에 반영된다.
- **STEP8 미실행 시**: 교차검증 시트/섹션이 비어 있으면 오류가 아니라 "추가자료 교차검증을 수행하지
  않음"으로 표시한다(테스트로 확인).
- **실제 브라우저 버그를 발견해 수정함**: `docx` 패키지의 `Packer.toBuffer()`는 Node의 `Buffer`에
  의존해 브라우저에서 "nodebuffer is not supported by this platform" 오류로 실패했다. 브라우저에서
  실제로 다운로드해보고서야 발견했고, `Packer.toArrayBuffer()`로 교체해 해결했다(Node 테스트만으로는
  잡히지 않는 종류의 버그였다 — 이 프로젝트에서 브라우저 실측 검증이 실제로 버그를 잡은 사례).
- **출력 옵션**: 손상목록/손상사진/교차검증/출처/검수이력/미연결사진 포함 여부를 체크박스로, 출력
  범위는 손상 No를 콤마/공백으로 입력해 "선택 손상만"으로 좁힐 수 있다(비우면 전체).
- **파일명**: `generateFileName()`이 파일명에 쓸 수 없는 문자(`\/:*?"<>|`)를 제거하고
  `{프로젝트명}_{종류}_{YYYYMMDD}.{ext}` 형태로 만든다.
- **출력 이력**: Excel/Word/PDF 각 시도(성공/실패)를 `ExportHistoryEntry`로 기록해 화면 하단에 표시한다.
  하나가 실패해도 나머지 형식은 독립적으로 계속 시도할 수 있다(버튼이 각각 분리돼 있어 자연히 만족).
- **원본 데이터 보존**: Excel/Word/PDF 생성 함수는 모두 입력 배열을 읽기만 하고 새 배열/객체를
  만들어 반환한다 — `damageRecords`/`photoRecords` 원본을 변경하지 않는다(테스트로 확인).
- **향후 확장 지점**: `ReportTemplate` 타입(`id/name/version/sections/styles/tokens`)만 정의해 두고
  템플릿 편집기는 만들지 않았다 — 스펙이 요구한 "확장 가능한 구조만 마련" 범위를 그대로 따랐다.

## 알려진 제한 사항 (최소 구현으로 남겨둔 부분)

- **모바일/좁은 화면 전용 레이아웃 없음**: STEP9 스펙 26번이 제안한 "손상목록→상세→사진→검수" 좁은
  화면 전용 전환 흐름은 구현하지 않았다. 현재 화면은 데스크톱 3분할 레이아웃(필터/테이블/Inspector
  모달) 하나만 제공하며, 좁은 화면에서는 가로 스크롤로 대응한다.
- **손상-사진 확정 연결**: STEP7 범위. STEP6은 매칭 점수만 계산해두고 연결을 확정하지 않는다.
- **추가자료 파일 업로드의 실제 브라우저 종단 테스트 미실시**: 이 환경에는 `<input type="file">`에
  파일을 자동으로 채워 넣는 도구가 없어, Excel/Word/PDF 추가자료 파싱(`loadDocuments.ts` 및
  `parseAdditionalExcel/Word/Pdf.ts`)은 화면 UI 렌더링 확인과 순수 로직 단위 테스트
  (`additionalDocs.test.ts`, `crossValidate.test.ts`)로만 검증했습니다. 실제 파일 첨부 시 결과를
  확인해 주세요. `.doc`(97-2003)는 지원하지 않습니다(.docx로 변환 필요).
- **중복 자료 탐지는 근사치**: 같은 자료 종류의 손상명+위치 후보 집합이 80% 이상 겹칠 때만 "중복 자료
  후보"로 표시하는 단순 휴리스틱입니다. 파일을 임의로 삭제하지는 않습니다.
- **출처 → PDF 페이지 뷰어 연동**: 현재는 페이지 번호와 발췌 텍스트를 모달로 보여주는 최소 기능입니다.
  PDF 뷰어를 열어 해당 페이지로 스크롤하는 기능은 포함되어 있지 않습니다.
- **실제 임베디드 이미지 PDF를 통한 종단 검증 미실시**: `photoExtraction.ts`의 bounding-box 계산/크롭
  로직은 타입 검사와 코드 리뷰로 검증했으나, 실제 사진이 포함된 PDF로 자동화 브라우저 테스트를 수행하지는
  못했습니다(테스트 환경에 파일 업로드 자동화 도구가 없음). 실제 보고서로 최초 사용 시 결과를 확인해
  주세요. 스캔본처럼 페이지 전체가 하나의 이미지인 경우 그대로 크롭되어 "페이지 전체를 덮는 이미지" 메모와
  함께 검토 상태로 남습니다.
